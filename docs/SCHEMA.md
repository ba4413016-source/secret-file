# مخطط البيانات — المرحلة الأولى

قاعدة البيانات PostgreSQL 15+ ضمن Supabase. ملفات المصدر التنفيذية في `supabase/migrations/`، والـ seed المحلي الخيالي في `supabase/seed.sql`. كل جداول `public` مفعّل عليها RLS؛ المنح تحدد العملية المسموحة، وسياسات RLS تحدد الصفوف المسموحة. لا يحتوي هذا المخطط على البريد أو كلمة المرور أو مفاتيح المصادقة.

## الحسابات والملفات الشخصية

- `auth.users` هو مصدر المصادقة الذي تديره Supabase. `public.users` ملف عام مرتبط به عبر `id` مع `ON DELETE CASCADE`، ولا يكرر بيانات تسجيل الدخول.
- `users` يحتوي اسم المستخدم الفريد، الاسم المعروض، النبذة، مسارات الصور، الدور والرتبة والتوثيق وXP وحقول المحامي وتفضيلات الملف والرسائل واللغة والمظهر. حقول الدور والتوثيق والرتبة وXP وبيانات اعتماد المحامي غير قابلة للتعديل من العميل. سياسة الملف الشخصي تنفذ إعداد `public / investigators / followers / private` وتمنع الاطلاع المتبادل عند وجود حظر.
- ينشئ trigger ملفًا آمنًا افتراضيًا بعد إنشاء مستخدم Auth. الاسم الأولي آلي وغير مرتبط بالبريد. التحقق من اسم المستخدم وتغيير الاسم مرة كل ستة أشهر يتمان داخل قاعدة البيانات.
- `social_links` روابط خارجية يملكها المستخدم؛ إظهارها مرتبط بخصوصية الملف وخيار إظهار الروابط.
- `user_follows` و`user_blocks` تدعمان صلاحيات المتابعة والرسائل وإخفاء الملف. يمكن للمستخدم متابعة أو حظر حسابه بنفسه فقط.

## القضايا والتقدم

- `cases` بيانات القضية وحالتها. القراءة العامة تقتصر على القضايا المنشورة. إنشاء المستخدمين، إن فُعّل في الواجهة، ينشئ قضية خيالية قيد المراجعة ولا يتيح النشر الذاتي.
- `case_suspects` و`case_evidence` محتوى القضية المنشور. تستخدم الأدلة `storage_path` بدل رابط عام.
- `case_solutions` منفصل عن محتوى القضية. لا يقرأ الحل إلا المستخدم الذي لديه تقدم مكتمل في القضية أو مسؤول موثوق.
- `case_progress` خاص بصاحبه. يمكن للعميل بدء قضية منشورة وتحديث `current_stage` و`client_state` فقط؛ لا يمكنه اعتماد الحالة المكتملة أو رفع نتيجته أو مكافآته.
- `user_notes` و`clue_connections` خاصة بالمستخدم. وصلات القرائن لا تُنشأ إلا لقضية بدأ المستخدم تقدمها.

## المجتمع والرسائل والمكافآت

- `theories` و`theory_comments` قابلة للقراءة العامة بعد اعتمادها، وتبدأ مساهمات المستخدمين قيد المراجعة. `theory_votes` قابل للقراءة والتعديل من صاحب التصويت فقط.
- `conversations` لا ينشئها العميل مباشرة؛ يجب أن ينشئها خادم موثوق بعد قبول طلب. يقرأها المشاركَان فقط.
- `message_requests` يقيّد الطلبات بسياسة استقبال الرسائل، وعلاقة المتابعة، والحظر. `messages` لا يقرأها أو يرسلها إلا طرفا محادثة نشطة؛ الرسائل المرسلة للمستخدم محدودة بـ 50 في اليوم بتوقيت UTC عبر trigger وقفل معاملات.
- `notifications` خاصة بالمستلم؛ يمكنه فقط تحديث `read_at`.
- `achievements`, `daily_challenges`, `mystery_boxes`, `seasons` بيانات تعريفية تقرأ وفق حالة النشاط. جداول `user_achievements`, `user_rewards`, `season_progress`, `leaderboard_entries` تُحدّثها جهة موثوقة، مع قراءة خاصة أو عامة حسب نوع السجل.
- `user_reports` يرسلها المستخدم عن مستخدم آخر وتظل تفاصيلها خاصة بصاحب البلاغ وفريق الإدارة. `audit_logs` للقراءة الإدارية فقط ولا يكتبها العميل.

## مصفوفة الصلاحيات المختصرة

| المجال | قراءة العميل | كتابة العميل |
|---|---|---|
| الملف والروابط الاجتماعية | حسب خصوصية الملف | حقول الملف المسموحة وروابطه فقط |
| القضايا والأدلة | محتوى منشور | إرسال خيالي للمراجعة؛ لا نشر ذاتي |
| التقدم والملاحظات | تقدم وملاحظات المالك | حالة الواجهة والملاحظات؛ النتيجة server-managed |
| النظريات والتعليقات | معتمدة أو مساهمة صاحبها | إنشاء/تعديل مساهمة غير معتمدة لصاحبها |
| الرسائل | أطراف المحادثة | طلب رسالة، أو إرسال ضمن محادثة قائمة؛ 50/يوم |
| الشارات والنتائج والسجلات | وفق سياسات الملف أو الإدارة | خدمات موثوقة فقط |

تظل `service_role` صلاحية خادمية فقط لأنها تتجاوز RLS. لا تستخدمها في كود المتصفح. تهيئة أول مسؤول لا تتم عبر seed؛ يلزم إجراء إداري موثوق خارج هذا الترحيل.

## بيانات التطوير والحدود الحالية

`seed.sql` يضيف قضيتين خياليتين، مشتبهين وأدلة وحلولًا وشارات وتحديًا يوميًا. لا يضيف أي حساب أو بريد أو كلمة مرور أو رمز. لا تحتوي هذه الدفعة على إعداد Storage buckets أو سياسات `storage.objects` أو إعداد Google OAuth الفعلي أو Functions/Realtime؛ تلك تحتاج إعدادًا منفصلًا ومفاتيح لا توضع في المستودع.
